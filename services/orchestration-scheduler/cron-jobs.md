# orchestration-scheduler задания по расписанию

Работает с PostgresSQL:

- База данных `joposcragent`
- Схема `orchestration`
- Таблица `scheduler` (по одной строке на `job_type` типа
  `orchestration.scheduler_jobs`; уникальность по `job_type` в схеме БД)

Работает с топиками Kafka:

- `collection-batch` — только для `job_type` = `COLLECTION_BATCH`

## Типы задач (`job_type`)

- **`COLLECTION_BATCH`** — пакетный сбор по расписанию; при наступлении
  `next_run` публикует сообщение в Kafka (см. ниже).
- **`RETENTION`** (и будущие значения `scheduler_jobs`) — полезная нагрузка
  в этой спецификации **пока не описана**; поведение добавят позже. Если строка
  расписания для такого `job_type` есть, демон **всё равно** продвигает
  `next_run` по `cron_expression` (ветка 4.2), чтобы расписание не замирало;
  Kafka и прочие действия до появления спеки не выполняются.

## Тик планировщика

Демон с периодичностью **раз в 10 минут** выполняет тик планировщика.

Спецификация исходит из **одного экземпляра** сервиса с одним таймером;
поведение при нескольких репликах без координации здесь не определяется.

Алгоритм работы:

1. **Оперативный кэш** — снимок **всех** строк `scheduler`: по каждому
   `job_type` хранятся `next_run`, `cron_expression` и дополнительно
   `previous_run` (только в памяти процесса: момент последнего срабатывания шага
   4 для этого типа; при старте и полной перезагрузке кэша — `null`, пока тик
   не сработает). Нет строки в БД для типа — нет записи в кэше для этого типа.
   Таблица пуста — кэш пуст.
2. **Старт сервиса** — один раз загружает **все** строки `scheduler` в кэш по
   ключу `job_type`; при пустой таблице кэш пуст.
3. **Периодический тик (раз в 10 минут)** — **без чтения БД** для решения о
   запуске:
   1. если кэш пуст — выход;
   2. иначе для **каждого** `job_type` в кэше **независимо**:
      1. если `now` строго раньше `next_run` для этого типа — для типа ничего;
      2. если `now >= next_run` (как у `timestamptz` в БД) — для этого типа
         переход к шагу 4.
4. **Срок наступил для `job_type` = `T`** — ветки 4.1 и 4.2 для `T`
   **параллельно**: порядок завершения не гарантирован; ветки не блокируют
   друг друга. Срабатывания разных `T1`, `T2`, … в одном тике тоже не должны
   блокировать друг друга.
   1. **Ветка 4.1 — действие по типу**:
      1. если `T` = `COLLECTION_BATCH` — сообщение в очередь:
         1. topic: `collection-batch`
         2. `jobUuid` = новый uuid
         3. `parentJobUuid` = `null`
         4. `entityUuid` = `null`
         5. `data` = `null`
      2. иначе — без Kafka и иных побочных действий (кроме 4.2 для типов вроде
         `RETENTION`).
   2. **Ветка 4.2 — следующий `next_run` для строки с `job_type` = `T`**:
      1. следующий момент после `now` по `cron_expression` из кэша для `T`
         (семантика crontab как в продукте);
      2. сначала кэш для `T`, затем колонка `next_run` в БД для `job_type` =
         `T`;
      3. ошибка записи в БД — в лог.

После успешного `PUT` из [REST API][rest-spec] сервис **инициирует
перечитывание** оперативного кэша из БД для затронутого `job_type` (см.
[REST: синхронизация кэша][rest-cache]).
